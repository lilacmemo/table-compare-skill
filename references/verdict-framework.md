# 结论框架与竞争话术规则（保真层 / 可编程层 / 支持度分级 / 可修改性）

> 来源：SpreadJS vs Univer 图表模块实战中多次被证据打脸后的修正沉淀。核心教训：粗粒度的"支持/不支持"结论会被对方任何一层的反证推翻；✅/⚠️/❌ 粗标记会被"有 UI 可改/模型层有值"推翻，呈现层改用 S1～S5 支持度分级。

## 判定基准原则（2026-11-04 用户定版，最高优先级，覆盖以下旧规则中冲突处）

四条原则，所有模块（图表/公式/后续全部维度）统一遵循：

1. **只对比商用版本**：SpreadJS（商业版）vs Univer Pro，**不与开源版做任何对比**。矩阵结论一律不再标注"开源版如何"。
2. **导入判定**：观察图表是否保留、各配置项是否正确（与 Excel 基线一致）。
3. **代码调用只认官方公开 API**：必须用**官方公开 API**（官方文档/reference 站收录的 API 及其文档化参数/枚举）调用成功，才算"支持"。
4. **导出判定**：与导入同等口径——导出文件中图表是否保留、各配置项是否保留且正常显示。

**配置项支持性判定规则（硬规则）**：
- **有公开 API 且调用成功** → 支持（= S1）
- **有公开 API 但调用不成功/设置不生效** → 特殊标记"API 缺陷"（支持声明存在但实测失效，单列统计，不算支持也不算不支持）
- **无公开 API（含运行时实测可用但文档未收录）** → **一律判不支持**（原 S2 类项全部降级；运行时实测结果可作为附注信息保留，但结论为"不支持"）

**适用范围补充（2026-11-05 用户确认，公式类模块同样执行）**：
- 11 个公式功能模块（跨工作簿/跨表/表格公式/按范围计算/循环引用/异步计算/目标求解/公式追踪/公式编辑器/公式隐藏/函数本地化）已按此口径逐项重核，证据必须落到**文档页面 URL**；`.d.ts` 与源码只能当"能力线索"，不能进矩阵。
- 典型剔除案例：Univer `SetTriggerFormulaCalculationStartMutation.dirtyRanges`（区域重算，命令层可传但未文档化）、`FormulaEditor` React 组件（包内导出但无组件文档）——两项均判"不计入支持"。
- **否定结论优先引官方文档原文**：Univer 官方功能对比页写明"不提供内置单变量目标求解""不提供内置单/双变量模拟运算表及方案管理器"，比"源码 grep 0 命中"更硬，也经得起客户复核。

与旧 S1～S5 的映射：S1=支持；S2→**不支持（附注：运行时实测可用，无文档，版本演进风险）**；S3/S4/S5 维持原判（均属不支持范畴，细分保留供话术使用）。

> 定版背景：用户明确"我们现在有实质性的误差（商业竞争场景），不能去直接扫产品的包"——依赖运行时枚举/内部结构得出的"可用"结论不具备商业口径的合法性，官方公开文档是唯一契约。

## 公式模块两级判定链（2026-11-07 v3 定稿，取代 2026-11-04 版容差口径）

公式函数模块的"支持/一致"判定独立于配置项 S1～S5，按**两级**进行，呈现时严格分开：

1. **第一级：是否支持**——产品写入公式后返回 `#NAME?` = 函数未实现，判"不支持"，**不参与值比较、不计入"不一致"**。支持度分母 = 参测用例数（本模块 500，含 5 条易失函数与 `IMAGE`）；环境依赖函数（`CALL`/`RTD`/`CUBE*` 等，Excel 也给不出 oracle）与单独搭场景的 4 条不进分母。
2. **第二级：是否一致**（仅对支持项）——**数值按 Excel 自身的 15 位有效数字归一后逐字比，文本（含复数）原样逐字比，不设相对容差**。措辞必须写"位数归一，不是容差"：15 位以内差一位就判不一致。布尔 vs 0/1 记「类型不同（布尔/数值）」单列（值等价但类型不同，对 ISLOGICAL/TYPE/EXACT 类下游调用有真实影响，销售可打这点但勿夸大为"算错"）；其余差异按性质分桶（精度/随机·时间/区域设置/格式/类型语义/功能/报错）。
   - **为什么不再用 1e-9 相对容差**：1e-9 会把 `BESSEL*`（差 1e-8）四条和复数 26 条全判 PASS，报告变成"两家都对"，客户逐位对账时一导出就露。逐字比之后，差异按幅度分档（≤1e-12 / ≤1e-9 / ≤1e-6 / ≤1e-3 / >1e-3）呈现，"差 1e-15"与"差 1e-6"分得清。
   - **为什么不是 17 位严格相等**：double 能表示 17 位，但 Excel 只显示、只存储 15 位。按 17 位比，`=PI()` 在两家都被判"不一样"，排名会反转（实测 SJS 58.06%、Univer 59.96%），比的是"谁输出位数接近 17 位"，不是"谁算得准"。
3. **用例准入红线（四原则①）**：每条用例必须先在 Excel 365 本体返回真实值（Excel oracle 逐条评估），Excel 自己都报错的用例禁止入库——"错误类型对比"是伪命题。
4. **双口径对账（四原则④）**：xlsx 活公式判定（LEFT 判 #NAME? → 15 位有效数字文本比 / 布尔 / 文本分支）与 Python 脚本判定必须逐行对账 0 不一致；口径修改时两处同步改，防止"说明改了格子没改"。
5. **差异可解释性**：每个差异项归入性质类别并写"可能原因"（精度 ～1e-8 属正常实现差异；RAND/NOW 属预期；DOLLAR 货币符号属区域设置），差异明细单独成 sheet 供人工复核。
6. **易失函数豁免（2026-11-05 用户定版）**：NOW/TODAY/RAND/RANDBETWEEN/RANDARRAY 只判"是否支持"（支持且返回非错误值 → 记「支持（易失函数，结果不对比）」），**结果不做对比、不计入一致也不计入不一致**。理由：每次重算结果都变，值对比无意义；判"不一致"会虚增差异量并误导结论。呈现时单独成行（如结论页"其中：易失函数"），用黄色/中性标记与真实差异区分。`IMAGE` 同理（无标量答案，只计支持度）。
7. **两个分母，永远不混算（2026-11-07 定稿）**：**支持度** = 支持数 ÷ 参测用例（500）；**准确度** = 形状与每格结果全对 ÷（该家支持数 − 该家支持的易失数）。`#NAME?` 只扣支持度，绝不进准确度分母——否则"函数少但算得准"与"函数全但算不准"会被混成一个数。对外写 `分子/分母 = 百分比`，并注明分母是哪一个。

## 两分法：每个能力项拆两层下结论

| 层 | 含义 | 验证手段 |
|---|---|---|
| **保真层**（Fidelity） | xlsx 导入还原既有图表的能力——文件进来后图表元素/样式/尺寸是否保留 | 三向验证：Excel 显式样式文件 → 导入读内部模型 → 截图 → 再导出解包 XML |
| **可编程层**（Programmability） | API 代码创建/修改图表元素的能力——开发者的配置面有多深 | 文档下探到 reference/类型定义层 + 运行时 setter 探测 + 实际调用验证 |

两层**可能严重背离**：实战中 Univer 保真层全链路出色（字体/颜色/图例位置/数字格式/gapWidth 导入导出还原），但可编程层文档缺失严重（setLegend 字体参数零文档）。

## 可修改性通道四分法（2026-11-02 增补，用户方法论贡献）

"接口文档没写"不等于"改不了"。每个配置项按四通道判定，判定顺序 **UI → API → 模型**：

| 通道 | 含义 | 判定手段 |
|---|---|---|
| ① 文档化 API | 官方文档写明 setter | reference 站查证 |
| ② 未文档化 API | 运行时实测可用但文档缺失 | setter 探测 + 试调用读回验证 |
| ③ 内置 UI 面板 | 产品自带面板可改 | **右键图表探测编辑菜单/面板**（Univer：右键 → Edit chart → Setup/Customize tab） |
| ④ 仅模型层保留 | 值存了但无任何读写入口 | resources 内部模型抓取（Univer：SHEET_CHART_PLUGIN） |

**实战教训**：Univer 的 Customize UI 面板能力远超 Facade 文档——刻度线位置/长度/粗细/颜色、标签旋转、坐标轴反转、min/max、对数、数字格式、趋势线（Add trendline）、系列透明度/边框全有 UI 控件。漏测 UI 会把对方"UI 能改"误判为"不支持"。

## API 支持度：只给 PASS / FAIL（2026-11-05 用户定版，取代 S1～S5）

用户原话：**"当前 api 的判断通过等级 s1 s2 看着很乱。你直接给 pass 和 fail 都遵照公开 api。不要魔改。"**

规则：

| 判定 | 条件 |
|---|---|
| **PASS** | 运行时存在公开 API，且调用成功（不抛错） |
| **FAIL** | 运行时没有公开入口，或调用即抛错（含"只有枚举没有方法""只有界面能点"） |
| **N/A** | Excel 本身没有这项能力，不计入分母，附录单独标注 |

- **不要**再引入 S1/S2/S3/S4/S5、"有文档/无文档""值在但没入口"这类中间档——对开发者来说它们都是同一件事：写不了。
- "能不能读回"不要参与 PASS/FAIL，单列一列（附录备注 / 五维评分里的「可读回」）。读不回不等于没有 API。
- 失败项必须写清 FAIL 的原因（无公开入口 / 调用抛错），原因比档位有用。
- 统计口径：PASS 率 = PASS /（PASS + FAIL），分母剔除 N/A 项；N/A 项另起一行说明"Excel 本无、我方可做"。

历史沿革（仅供理解旧报告）：S1～S5 是 2026-11-03 为图表模块设计的分级，本意是区分"代码能改"与"界面能点"。在图表模块它有效，因为确实存在"UI 面板能改但零 API"的情况；但套到格式/条件格式这种"要么有 setter 要么没有"的模块上，七档分级的区分度淹没在噪音里，故停用。**图表模块旧报告里的 S1～S5 不要求回改，新写的对比一律 PASS/FAIL。**

## 判定红线 ①：API 通 ≠ 效果对 —— UI 降级一律 FAIL（2026-11-06 用户定版）

用户原话：**"如果代码能调用通过，但是 UI 上观察到展示异常也不能算 PASS，要按 Fail，同时说明原因。例如 SpreadJS 代码虽然可以添加 3D，但其实 3D 图会降级，这种也不能算支持 Pass。"**

| 判定 | 条件 |
| :-- | :-- |
| **PASS** | 有公开 API、调用成功、读回一致，**且用户在实际界面上看到的效果没被降级** |
| **FAIL** | 缺 set / 缺 get / 读回被改写 / 调用抛错 / **API 通但 UI 降级** —— 说明列必须写清是哪一种 |

为什么必须这样：报告读者不写代码，只看效果。"我们 API 能设 3D" 和 "用户看到 3D" 是两件事，混为一谈等于骗人。

已确认的例子：

| 能力 | API 层 | UI 层 | 判定 |
| :-- | :-- | :-- | :-- |
| SpreadJS 3D 图表类型 | `chartType(columnClustered3D)` 调用成功、读回 15 一致 | 画布上是**平面 2D**，无厚度/透视 | **FAIL（UI 降级）** |
| SpreadJS 页脚 `&F` 令牌 | `footerRight('&F')` set 成功、读回一致 | 预览与导出的 PDF 里**整段消失**（`&D`/`&P`/`&N` 都正常） | **FAIL（UI 降级）** |

落地方式（双引擎对比台）：
1. 台账 `js/data/ui-downgrade.js`：`window.UI_DOWNGRADE[模块][用例ID] = { sjs: '原因', uni: '原因' }`。
2. 判定链 `applyUiDowngrade()` 在 `renderResults` 之前跑，只对**当前判 PASS 的那一侧**生效，把 PASS 改成 FAIL，原始 API 结论存 `result.sjsApi / uniApi`，说明列自动加「UI 降级：…」。
3. **进台账的门槛：必须真看过渲染结果**（截图 / 导出文件用 Excel 或 Chromium 打开对照）。凭印象"可能有问题"的一律写进文档「待复核」，不进台账。

**没逐项复核的怎么办**：报告只对"看过"的项下 UI 结论，其余按 API 层结论记录，并在方法说明里写清"UI 层抽样复核 N 项"。不许把 API 结论静默当成效果结论。

## 判定红线 ②：基准线一律取 Excel 本体（2026-11-06 用户定版）

用户原话：**"所有的比对原始都要基于 excel。"**

含义：任何"谁对谁错/谁强谁弱"的比较，基准值必须来自 **Excel 自己**——不是来自参评双方中的任一方，也不是"两家互相看"。

操作要求：

| 层次 | 基准怎么取 | 反例（都是踩过的） |
| :-- | :-- | :-- |
| 图表/配置项 | 样本 xlsx 由 Excel 造（COM），基准值取 Excel 的 UI 默认与对象模型 | 用 openpyxl 造样本，DrawingML 细节缺失，被用户否掉重造 |
| 页面设置 | COM 读 `PageSetup`（方向/纸张/缩放/边距/页眉页脚/居中/网格线）→ `out/data/*-excel-oracle.json` | 拿 SpreadJS 的 `printInfo()` 当基准，等于让考生自己出题 |
| 打印输出 | Excel `ExportAsFixedFormat` 出 PDF，逐页比页数/方向/尺寸/文本层 | 只比"两家导出的 PDF" |
| 公式 | Excel 365 实算值当 oracle（活公式 sheet），五条用例原则见公式模块 | 用第三方库算值 |
| 效果层 | Excel 打开/打印的结果当"正确答案"图 | 把某家 SDK 的渲染当标准 |

**写报告时的硬要求**：凡是"一致 / 不一致"的结论，表里必须有 **Excel 那一列**。没有 Excel 列的三方对比，只能写成"两家行为差异"（描述），不能写成"谁不对"（判定）。

## 话术规则

1. **禁止说"对方不支持 X"**——除非 UI 面板 + API 层 + 内部模型层三层都证明缺失。对方任何一层还原了 X，"不支持"的说法当场被打脸，话术可信度清零。
2. **对方能力"深埋"时的正确话术**：不说"没有"，说"**我们的全部配置项都有正式文档、开箱可查、开发效率可预期；对方同类能力分散在 UI 面板/未公开 builder 层/未文档化参数三处，程序化开发试错成本高，升级随时可能变**"。
3. **禁止说"对方不能配置"**——对方内置 UI 面板可能什么都能改（Univer Customize 面板即如此）。同样**禁止说"我方没有 UI"**——SpreadJS 有设计器组件（在线表格编辑器：功能区/公式栏/侧面板/上下文菜单，可嵌入应用，需单独部署许可；数据图表另有 DataChartConfigPanel 配置面板）。正确口径："对方配置能力分散在 UI 面板/builder/未文档化参数三处，程序化开发试错成本高，部分配置无任何修改入口；我方 API 全文档化 + 设计器组件提供可选 UI 能力"。
4. **保真层劣势的正确话术**：用可量化的用户体验差异——"对方导入后图表默认不可见（0×0 或几像素），需逐个手动修复；我们导入即可见即可编辑"。附 size 分布量化证据 + Chrome 有头截图。
5. **避开战场清单**：双方都弱或对方独有的能力（如 SJS Data Charts、对方独有协同能力）单独归类，不进入主打话术。
6. **每条话术必须挂证据**：证据图 + 复现步骤，无证据的话术不写进报告执行摘要。

## 版本分层口径

- **（2026-11-04 收紧）**参评双方固定为商用版本：SpreadJS（商业版）vs Univer **Pro**。矩阵结论不再写开源版行为，调研阶段的开源版信息仅供背景理解，不进入结论。
- 官方功能清单（如 SpreadJS《功能清单 vX.Y》）中标注"新增/增强"的项是版本差异话术素材库。
- 我方 npm 包版本也要注明 scope：@grapecity-software（官方中文渠道，可能滞后）vs @mescius（海外渠道），实战中前者最新版比后者少 3 个补丁版。

## 修正轨迹纪律

- 报告版本演进记录每轮修正（v1→v2→v2.1…），被推翻的结论保留原结论+修正原因，不静默改写——这既是诚实的体现，也防止同一误区在不同模块重犯。
