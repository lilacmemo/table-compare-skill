# 公式函数模块作业指导（v3，2026-11-07 定稿）

回答一个问题：**同一个函数、同一条公式，参评方算出来的结果和 Excel 一样不一样。**
不做精度误差分析、不做位数归因、不设容差档——只给"一样 / 不一样 / 不认识"三种判定，然后换算成两个百分比。

---

## 1. 两个分母，永远不混算

| 指标 | 定义 | 本轮值（SJS 19.2 vs Univer Pro 1.3.1） |
| :-- | :-- | :-- |
| 进分母的函数 | 519 个函数 − 15 条无 oracle = **504** | 500 条主表 + 4 个特殊函数（7 条用例，一个函数一票） |
| **支持度** | 能算出结果 ÷ 504（`#NAME?`、写入被拒 = 不支持） | **494/504 = 98.02%** ｜ **491/504 = 97.42%** |
| **准确度** | 形状与每格结果全对 ÷（支持数 − 5 易失 − `IMAGE`） | **448/488 = 91.80%** ｜ **324/485 = 66.80%** |
| 一次跑通 | 全对数 ÷ 504（含不支持的函数） | 448/504 = 88.89% ｜ 324/504 = 64.29% |
| 多值溢出 | 全对数 ÷ 36 | 34/36 = 94.44% ｜ 29/36 = 80.56% |

- `#NAME?` **只扣支持度**，绝不进准确度分母——否则"函数少但算得准"和"函数全但算不准"会被混成一个数。
- 对外永远写 `分子/分母 = 百分比`，并注明分母是"504 个函数"还是"支持数 − 6"。
- **能测的就要进分母**：只要该函数有 Excel 标量真值，哪怕要另造样本（透视表、多工作表），也算进 504。客户会问"这几个为什么不参与"——只有"本机给不出 oracle"才够格排除。
- 支持度与准确度的差，就是这个模块最值钱的一句话：**覆盖面两家差不多（差 3 个），准确度差 25.0 pp**。

## 2. 判定尺子：先标定，再出数

### 2.1 三步标定（不通过就不许出数）

1. **必然正确的用例两家都要过**：`=1+1`、`=PI()`、`=SUM(A1:A6)`。若 `=PI()` 有一家被判"不一致"，尺子错了，不是产品错了。
2. **必然错误的用例两家都要不过**：人为造一条差 1e-3 的对照，必须判不一致——证明尺子没有松到什么都放行。
3. **排名要符合已确认的能力事实**：跑出反直觉结果（例如"被普遍认为精度差的那家反而更高"）时，先怀疑尺子，不许先写结论。

### 2.2 数值按 Excel 的 15 位有效数字归一，文本原样

- **数值**：转成 15 位有效数字的文本再逐字比。Excel 自己只显示、只存储 15 位（`1.04719755119660`），引擎内部是完整 double；按 17 位比会把"精度完全够用"判成差异。
- **文本（含 `IM*` 复数）**：**原样逐字比**，不折算。复数返回的是一段拼出来的文本，谁多写几位谁就不同，这一族是全模块最严的一档（SJS 24/26 = 92.31%、Univer 23/26 = 88.46%）。
- **这是位数归一，不是容差**：15 位以内差一位就判不一致。

### 2.2.1 先把 SpreadJS 的计算精度也设成 15 位（本轮定稿口径）

只在"比较时"把 Excel 归一到 15 位是不够的：SpreadJS 内部按完整 double 算、拼文本时默认写 17 位，同一份正确结果会被判"不一致"。**对比前先把引擎拉到同一起跑线**：

```js
GC.Spread.CalcEngine.Functions.CALC_PRECISION = 15;   // 静态属性，必须在 new Workbook 之前
```

- 建完 Workbook 再设无效；对比台 `js/app.js` 启动段、跑批 `tools/run_cases.js` 都默认设 15。
- Univer 没有对应开关（它本来只写 12 位左右），比较时同归一到 15 位。
- 这一档的收益：26 条复数用例 11/26 → 24/26，主表 PASS 438 → 450；数值末位那 37 条不受影响（差在 15 位之内，设不设都一样）。
- 历史数据要复现就显式退回：`?prec=default` / `--prec-default`。

> **反例（本轮实测，务必记住）**：按"double 严格逐位相同"重算，SJS 281/484 = 58.06%、Univer 289/482 = 59.96%——**后者反而更高**。因为两家都存不下 Excel 的 17 位，`=PI()` 在两边都被判"不一样"。这个尺子比的不是算得准不准，而是谁的输出位数更接近 17 位，会把正确答案判成错误。

### 2.3 不许加相对容差

设 1e-9 相对容差时，`BESSEL*` 四条（差 1e-8）全被判 PASS，复数解析成实部/虚部后 26 条也全过——报告会变成"两家都对"，而客户做逐位对账时一导出就发现对不上。
正确做法是**逐字比，再把差异按幅度分档**（≤1e-12 / ≤1e-9 / ≤1e-6 / ≤1e-3 / >1e-3），让"差 1e-15"和"差 1e-6"分开呈现。

### 2.4 豁免清单（哪些不进分母）

| 类别 | 函数 | 支持度 | 准确度 |
| :-- | :-- | :-- | :-- |
| 易失 5 条 | `NOW` `TODAY` `RAND` `RANDBETWEEN` `RANDARRAY` | 算（"认不认识"有效） | **不算**（值每次重算都变，比不出"一致/不一致"） |
| 环境依赖 15 条 | `CALL` `REGISTER.ID` `RTD` `WEBSERVICE` `STOCKHISTORY` `TRANSLATE` `EUROCONVERT` `JIS` + CUBE 全家 7 | **不算** | 不算（Excel 在同一份样本里也给不出 oracle，属"无法判定"，不是"不支持"） |
| 单独搭场景 4 条（7 条用例） | `GETPIVOTDATA` `SHEET` `SHEETS` `IMAGE` | **算**，一个函数一票计入 504（SJS 4/4、Univer 3/4） | 算；SJS 3/3、Univer 2/2。只有 `IMAGE` 无真值，只判支持 |
| `IMAGE` | 返回图片对象，Excel 本机也只回错误码 `0x800A0803` | 算（认不认识） | **不算**（没有标量答案） |

**动态数组固定开着测**（SJS `sp.options.allowDynamicArray = true`，Univer 无此开关）。关掉连 `SEQUENCE(5)` 都只回一个数，那不是能力差异，是配置没开。

### 2.5 比较前的值归一（五条，专防假差异）

同一个正确答案，两家可能以五种不同"包装"交回来。不先掰成同一种表示，会把算对的判成算错：

| 现象 | 例子 | 归一做法 |
| :-- | :-- | :-- |
| 数字格式 | Univer 给公式结果**自动套格式**：负金额套货币、比例套百分比，`getValues()` 读回 `(¥188.71)` / `8%` | 复算列先设「常规」再写公式，比较原始数值 |
| 日期 | SJS 读回 `Date` 对象、Univer 读回 `2020/03/15`、oracle 是序列号 `43905` | 按**本地墙钟字段**换算成 Excel 序列号（不能用 `getTime()` 直接减，东八区会差 0.667 天） |
| 时间小数 | `TIME(10,20,30)` 应得 `0.430902777777778` | 序列号**不四舍五入**：取整到 1e-9 会变成 `0.430902778`，把算对的判成差异 |
| 布尔 | `TRUE` 读回 `1` | 布尔 ↔ 1/0 |
| 存值≠显示值 | `=ACOS(0.5)` 存 `1.0471975511965976`（17 位），但 Excel 任何格式**最多显示 15 位**、常规格式只显示 10 位（`1.047197551`） | 读回取**存储值**不取显示文本；判定与对外文字统一按 15 位（Excel 能显示的上限），17 位只进 oracle 证据文件 |

**这五条是"表示归一"，不是放宽标准**：归一之后仍然不一致的，才是真差异。缺了第一条，曾把 11 个完全正确的财务函数判成"算不准"。

第五条最容易翻车：把 double 的 17 位照抄进"差异说明"，客户照着在 Excel 里敲一遍，看到的是 `1.047197551`，当场质疑数据造假。**引用 Excel 的值，位数不能超过 Excel 能显示的位数。**

## 3. 六步管线

1. **共享数据区 + 语义用例**：一个数据区定义三方共用（数值格 + 公式格），日期用 Excel 序列号存；每个函数一条"常规用法"用例，返回数组的不套 `INDEX`、让它自然溢出。用例公式必须落在有数据的表，脚本统一写到固定列、每条独占 12 行给溢出块留位。
2. **Excel oracle 先行**：Excel COM 逐条写入（`.Formula2`）→ `CalculateFullRebuild` → 取溢出块缓存值 → 抽成 JSON。500/500 必须全部出值；Excel 自己报错的用例当场修参数或剔除，**禁止拿错误码做"错误类型对比"**。
3. **双端同数据区跑批**：SJS 本地 Playwright（开动态数组）＋ Univer 本地 Pro 工程，同一条公式写同一列，读回整块结果。
4. **判定 + 对账**：Python 判定与 xlsx 活公式判定逐行对账，0 行不一致才算交付。
5. **特殊函数单独搭场景**（§4）。
6. **性能与导出**（§5、§6）：性能只看重算；导出只比公式（`<f>` 节点逐格，不用各家 `getFormula()`）。

## 4. 特殊函数：4 条要搭场景的（7 条用例，两个分母分开算）

**这一组同样要算准确度，不能因为"单独搭场景"就只报支持度**：7 条里 5 条 Excel 有标量真值（`SHEET`/`SHEETS` 3 条 + `GETPIVOTDATA` 2 条），两家在这 5 条上逐格相同。只有 `IMAGE` 两条 Excel 自己也返回错误码 `0x800A0803`、没有答案，才只判支持。

| 指标 | SpreadJS 19.2 | Univer Pro 1.3.1 |
| :-- | :--: | :--: |
| 支持度（÷ 4 个函数，一个函数一票） | 4/4 = 100.00% | 3/4 = 75.00% |
| 准确度（÷ 该家支持且有真值的函数数） | 3/3 = 100.00% | 2/2 = 100.00% |

**这 4 个函数已计入 504 分母**（SJS 494 = 490 + 4、Univer 491 = 488 + 3），§4 是它们的证据页，不是另一套数字。

结论落在"支不支持"，不落在"准不准"：`GETPIVOTDATA` 是唯一拉开支持度的一条。**报告正文只写函数口径**（能不能算、结果对不对），透视表插件、透视表导入渲染这些工程细节放工程文档，不写进客户报告——这一点用户明确要求过。

| 函数 | 场景 | SpreadJS 19.2 | Univer Pro 1.3.1 |
| :-- | :-- | :-- | :-- |
| `SHEET` / `SHEETS` | 两张表：`=SHEET()` / `=SHEETS()` / `=SHEET("明细")` | 2 / 2 / 1，全对 | 2 / 2 / 1，全对 |
| `GETPIVOTDATA` | Excel COM 建真透视表（金额合计 / 区域） | **2/2 全对（500 / 1520）** | **0/2，两条都 `#NAME?`** |
| `IMAGE` | 远程 URL + 替代文本 | 接住为图片对象（文本 `Picture` / `图`） | 返回空 |

### 4.1 `GETPIVOTDATA` 在 SpreadJS 上要插件

- 不装 `@grapecity-software/spread-sheets-pivot-addon` 就是 `#REF!`——**这不是函数不支持，是构建缺件**。
- **插件版本必须与主包完全一致**（本轮同为 19.2.2）。跨小版本注册失败，表现和"没装"一模一样，只会看到 `#REF!`。
- **脚本顺序**：core → pivot 插件 → **resources-zh** → designer。Designer 必须最后接管 Ribbon/UI。
- **关于界面语言（2026-11-09 更正）**：装插件后看到 `Row Labels` / `Grand Total`，**不是插件的固有限制**——真因是缺核心中文资源包 `@grapecity-software/spread-sheets-resources-zh`（`gc.spread.sheets.resources.zh.min.js`）。只切 `culture('zh-cn')` 无效：插件的 `SR.langs` 只有 `en`，zh-cn 槽位被英文兜底填满 358 键。补上资源包后（必须排在 pivot 插件之后，注册有 `GC.Spread.Pivot.SR` 守卫），面板、表头、`总计 / 值` 全部中文化，数值不受影响。判"中文表头丢失"先查这一条，详见 pitfalls 59。
- 装好后两条公式与 Excel 逐格相同，透视表结果区 `A3:B7` 数值全对。

### 4.2 判 Univer"不支持这个函数"前，先证明插件在

`GETPIVOTDATA` 的结论必须是"**透视表能力在，取值函数没有**"，分三层取证：

1. **插件在**：`@univerjs-pro/sheets-pivot` 在 advanced preset 依赖里，`UniverSheetsPivotTablePlugin` 随 preset 注册；`workbook.addPivotTable` 是 `function`、`worksheet.getPivotTableByCell` 可用。
2. **透视表被正确解析**：`getPivotTableByCell(2,0)` 返回对象（`id = xlsxPivot1`，带 `addField`），结果区 500 / 530 / 490 / 1520 全对。
3. **函数无实现**：无参 / 单条件 / 双条件三条全部 `#NAME?`；引擎包里 `GETPIVOTDATA` 只出现在函数名映射表、函数描述和语言包，`engine-pivot` / `sheets-pivot` 里搜不到实现。

**"包里 grep 得到函数名"不等于"这个函数能算"**——函数清单是给编辑器补全用的，只有真搭一张透视表才能发现。

## 5. 性能：重算看引擎，写入看写法

**测量场地 = 本地对比工程 `index.html`**（SJS 是 Designer 包裹的 Workbook、Univer 是 Pro 全套 UI，即客户实际形态），同一台机器、同一个无头 msedge，**每轮新开页面**，各跑 2 轮取**中位**。

| 指标 | SpreadJS 19.2.2 | Univer Pro 1.3.1 | 倍数 |
| :-- | ---: | ---: | :---: |
| 写数据 + 挂公式（事件/绘制/重算全挂起） | 1,285 ms | 2,646 ms | 2.06×（SJS 更快） |
| **全量重算（中位）** | **2,704 ms** | **13,195 ms** | **4.88×** |
| 改一个输入后重算 | 3,402 ms | 11,940 ms | 3.51× |

四条纪律：

1. **同一页面连续跑会退化**：Univer 第 2 轮重算从 11 s 涨到 22 s（旧簿 `dispose()` 后公式 worker 仍留着上一份数据）。必须每轮新开页面。
2. **取中位不取均值**：6 次极差占中位 SJS 45%（首轮 3,673 ms 是冷启动，去掉后 21%）、Univer 19%；均值会被一次抖动带偏，结论只讲到「约 5 倍」。
3. **批量写公式必须三样一起挂起**：`suspendEvent()` + `suspendPaint()` + `suspendCalcService()`，写完 `resumeEvent()` → `resumePaint()` → `resumeCalcService()`。只挂计算不挂事件，Designer 会对每条 `setFormula` 通知一次 Ribbon/状态栏，4.3 万条能把写入从 1.3 s 拖到 3.2 s——**3.2 s 是写法成本，不是引擎能力**，报数时不许拿它当 SpreadJS 的写入上限。Univer 没有等价开关，只能整段计时。
4. **条数按实际写公式的列算**：本轮 43,263 条 = `Data` 明细 4 列 × 10,000 + `Report` 240 + `Chain` 3,000 + `Dynamic` 23。`Data` 有 5 列数据但只有 4 列写公式，按 5 列统计会多算 10,000 条。

**等价性先验必做**：跑完抽 9 个格（明细、汇总、引用链、动态数组各取几个）双端取值逐字相同，才能排除"一边少算了一批"。

## 6. 定稿结论与话术

**数字**：支持度 494/504（98.02%）vs 491/504（97.42%），只差 3 个；准确度 448/488（91.80%）vs 324/485（66.80%），差 25.0 pp；多值溢出 34/36 vs 29/36；全量重算 4.88 倍（多轮 4.88–5.11×）。

**差异幅度必须一起说**：两家的差异**没有一条超过 1e-3**，SJS 37 条数值里 27 条在 1e-12 以内，Univer 157 条里 104 条在 1e-12 以内、52 条在 1e-9 以内——**没有量级错误，失分都在末几位或文本形态**。Univer 的低分集中在统计（43.93%）、财务（46.30%）、兼容性（32.50%）三个数值族，根子是它的数值输出位数比 Excel 少；SJS 现在最低的是财务与兼容性（都是 80.00%），工程族设了 15 位精度后从 66.67% 升到 88.89%（`BESSEL*` 仍差 1e-8）。

**失分构成**：**主表 500 条**下 SJS 50 = 不支持 10 + 文本 3（`BASE` 小写、`IMCOT`/`IMTAN` 实部末位）+ 数值末位 37；Univer 173 = 不支持 12 + 行为不同 4 + 数值末位 157。**对外 504** 口径再加 6 条只计支持度（5 易失 + `IMAGE`）→ SJS 56 / Univer 180；其中 Univer 多一条 `GETPIVOTDATA` 不支持，只看能判准确度的函数就是 **174**（= 13 + 4 + 157）。**173 / 174 / 180 三个数都对，分母不同不能混着用**——混了就会出现「失分率 34.52%」和「准确度 66.80%」加不到 100 的尴尬。

**能说**：
- 同一批 504 个函数、SpreadJS 按 15 位精度算、不设容差逐字比，我们 91.80%、Univer 66.80%（有逐条证据）。
- 函数覆盖 494 vs 491，差距只有 3 个；但准确度差 25.0 pp，可复现。
- 43,263 条公式的负载，全量重算 2.7 s vs 13.2 s，差 4.88 倍（多轮复测 4.88–5.11×；本地对比台、同机同浏览器、9 个抽样格对得上）。

**不能说**：
- "我们支持的函数多得多"（只差 3 个、0.60 pp）。
- "我们和 Excel 逐位一致"（`BESSEL*` 差 1e-8、复数 92.31% 逐字一致）。
- "Univer 财务函数算不准"（差异只在末位，不是财务算法问题）。
- "Univer 不支持透视表"（透视表能建能算能读回，缺的是 `GETPIVOTDATA`）。

## 8. 判定前自检七条

1. 支持度与准确度的分母写清楚了吗（504 vs 488/485，且说明扣了 5 易失 + IMAGE）？混算了吗？
2. `=PI()` 这类用例两家都过了吗？没过先修尺子。
3. 有没有用相对容差把真差异放过（`BESSEL*`、复数）？
4. SpreadJS 是不是在 new Workbook **之前**设了 `CALC_PRECISION=15`？跑批结果的 `env.calcPrecision` 是 15 吗？
5. 有 Excel 标量真值的特殊函数（`SHEET`/`SHEETS`/`GETPIVOTDATA`）进 504 分母了吗，还是被当成"单独一组"漏掉了？
6. 判"不支持"前，插件/装配确认过吗（SJS pivot addon、Univer advanced preset）？
7. 性能数字是不是"每轮新页 + 中位 + 只看重算"？负载条数按实际写公式的列算过吗？
